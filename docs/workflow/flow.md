# 실행 흐름과 사람의 자리

이슈 하나가 머지되기까지 무엇이 도는지, **사람은 어디서 멈춰 세우는지**.

---

## 전체

```
이슈        /prework          spec+plan       /work         개발          머지       문서
(사람)  →   요구·명세·분해  →  리뷰 요청  →  구현·리뷰  →  리뷰 요청  →  (사람)  →  정리
                                  ↑                              ↑
                              사람 승인                       사람 머지
```

`이슈 생성`·`쟁점 결정`·`승인`·`머지` 가 **사람만 하는 일**이다. AI 는 그 앞에서 멈춘다.

---

## `/prework <이슈번호>` — 착수 준비

```
이슈 읽기 → 문서 브랜치 → 요구사항 검토(쟁점만, 파일 없음)
                              │
                     쟁점이 있나? ──있음──▶ 사용자에게 선택지 제시 ─┐
                              │                                    │
                            없음 ◀───────────────────────────────┘
                              ▼
                        명세 작성(확정된 것만)
                              │
                   기존 명세로 충분한가? ──충분──▶ "갱신 불필요" 보고 후 확인
                              │
                            부족
                              ▼
                  task 분해 + (승인된 경우만) 결정 기록
                              ▼
                     spec+plan 리뷰 요청 1건 → 멈춤
```

**쟁점을 앞에서 끝낸다** — 명세 도중에 판단을 보류하면 "확정 후", "분기 A/B" 같은 흔적이
산출물에 남는다. 결정 게이트를 통과한 뒤로는 확정된 것만 현재형으로 쓴다.

**명세와 분해를 한 리뷰 요청으로 묶는다** — 승인 왕복을 1회로 줄이기 위함.

절차 정본: [`.ai/workflows/prework.md`](../../.ai/workflows/prework.md)

## `/work <이슈번호>` — 구현과 리뷰 루프

**이슈 하나가 브랜치 하나·리뷰 요청 하나다.**

경로는 **분해(`docs/plan/<번호>/`)의 유무**가 가른다. 라벨이나 제목으로 판정하지 않는다.
판정 기준은 로컬 작업 트리가 아니라 **원격의 통합 브랜치**다 — 로컬이 낡으면 이미 머지된
분해를 못 보고 승인 게이트를 건너뛴다.

**판정은 `script/work-preflight.sh` 하나가 한다.** 열린 리뷰 요청 → 분해 → 명세 순으로 보고
`plan` 또는 `standalone` 을 출력한다. 순서가 결과를 바꾼다 — 두 검사 사이에 spec+plan 이
머지되면, 분해를 먼저 본 경우 단독 task 로 오판한다.

| | 분해가 있다 | 분해가 없다 |
|---|---|---|
| 이슈 | 요구사항. task 가 그 안에서 커밋 단위로 돈다 | 단독 task. 그 이슈 자신이 구현 단위다 |
| 완료 조건 | `docs/plan/<번호>/task.md` | 이슈 본문 |
| task 이슈 동기화 | 돈다 | 건너뛴다 |

```
work-preflight.sh ──┬─ 착수 불가 ──▶ 멈춤
                    ├─ plan ──▶ sync-task-issues.sh ─┐
                    └─ standalone ───────────────────┤
                                                     ▼
                                        작업 하나 구현 + 테스트
                                                     ▼
                                          run-lint-test.sh
                                           │            │
                                         실패          통과
                                           ▼            ▼
                                      커밋 안 함     커밋 → 남은 작업?
                                        멈춤              │
                                                     없음 ▼
                                              리뷰 요청 1건
                                                     ▼
                                      review-mr.sh → post-review.sh
                                                     │
                     ┌──────────────┬────────────────┼──────────────┐
                   0 PASS        1 수정 필요       2 실패         3 상한
                     ▼              ▼                ▼              ▼
              남은 minor 처리    다시 구현        멈춤      리뷰 요청 열어 둔 채
              → 사람 머지 대기                                   사람에게
```

**구현과 리뷰는 서로 다른 도구가 맡는다.** 같은 모델이 자기 코드를 리뷰하면 같은 맹점을
두 번 지나간다. 설정이 그것을 강제한다 — 두 역할의 러너가 같으면 `harness render` 가 거부한다.

리뷰는 `script/review-mr.sh` 로만 돌린다 — 회차 라벨과 상한이 거기에만 있어, 그 경로를
건너뛴 리뷰는 상한 없이 반복된다.

### 루프가 멈추는 조건

**세션이 세지 않는다.** 회차와 반복 지적은 스크립트가 세고 스크립트가 멈춘다 —
세는 쪽과 멈추는 쪽이 같으면, 세지 않은 회차가 그대로 상한 밖이 된다.

| 조건 | 뜻 | 무엇이 멈추나 |
|---|---|---|
| blocker·major 0건 | 남은 minor 의 처리를 남긴 뒤 루프를 끝내고 함께 보고 | 등록 스크립트 (종료 코드 0) |
| 리뷰 회차 상한 | 더 고치지 않는다. 리뷰 자체를 수행하지 않는다 | 리뷰 스크립트 (종료 코드 3) |
| 한 파일에 blocker·major 가 연속 | **코드가 아니라 명세가 틀렸다.** 명세 단계로 되돌림 제안 | 등록 스크립트 (종료 코드 3) |
| 종료 코드 2 | **PASS 가 아니다.** 리뷰를 수행하지 못한 것 | 절차 |
| 검증 실패로 커밋 못 함 | 실패 출력을 그대로 보고. **무변경보다 먼저 본다** | 절차 |
| 재시도 회차에 커밋이 하나도 없음 | 남은 지적을 전부 이월·반증한 것이다. 재리뷰하지 않는다 | 절차 |

상한 값은 `harness.toml` 의 `review.max_rounds` 와 `review.repeat_file_max` 가 갖는다.
**판정은 리뷰 본문의 선언이 아니라 발견 등급 집계로 한다** — 선언은 계약 준수 여부를 보는 데 쓴다.

절차 정본: [`.ai/workflows/work.md`](../../.ai/workflows/work.md)

## 사람만 하는 일

| 지점 | 왜 사람인가 | 무엇이 막나 |
|---|---|---|
| 요구사항 이슈 생성 | 이슈 번호 없이는 커밋 불가 | `githooks/commit-msg` |
| **쟁점 결정** | 출처 충돌·규칙 개정이 걸린 판단은 사람 몫이다 | 요구사항 검토자에게 **쓰기 도구가 없다** — 결정을 문서에 남길 수단이 없고, 절차가 보고하고 멈춘다 |
| **결정 기록을 남길지** | 결정마다 기록을 만들면 아무도 읽지 않는다 | 결정 게이트의 **마지막 질문**. 작업 분해자는 승인 없이 만들지 않는다 |
| **보호 문서 수정** | 에이전트가 근거로 읽는 문서다. 근거가 흔들리면 판단이 전부 흔들린다 | 권한 설정의 deny + 명령 가드. 목록은 `harness.toml` 의 `docs.protected` |
| spec+plan 승인 | 명세가 틀리면 그 뒤가 전부 헛일 | 절차가 리뷰 요청 올리고 멈춤 |
| **결정의 확정** | 되돌리기 비싼 결정의 확정 | 효력은 통합 브랜치 머지에서 생긴다. 어느 에이전트도 머지하지 못한다 |
| 개발 리뷰 요청 머지 | 판정 PASS 는 의견이지 승인이 아니다 | 에이전트 금지 목록 |
| 리뷰 스레드 resolve | 자기 지적을 스스로 닫으면 리뷰가 형식이 된다 | 구현자 금지 목록 |
| 보호 브랜치 push | 보호 브랜치는 리뷰 요청으로만 반영한다 | **리뷰 호스트의 서버 설정**(최종) + `githooks/pre-push` + 권한 deny + 명령 가드 |
| 커밋·push 지시 | 명시적 지시 없이는 하지 않는다 | `.ai/AI_AGENT.md` 의 "금지 사항" |

### 가드레일 층

문서로만 금지하지 않는다. 층마다 구멍이 달라서 겹쳐 둔다.

| 층 | 막는 대상 | 우회 |
|---|---|---|
| 리뷰 호스트의 보호 브랜치 설정 | 보호 브랜치로의 모든 push | **없음. 실제 최종 방어선** (서버 설정) |
| 권한 deny | 에이전트가 실행하려는 명령 | 사람의 직접 실행은 못 막음. 패턴이라 변형을 다 덮지 못함 |
| 명령 실행 전 가드 | 명령을 파싱해 실행 **전**에 판정 | 그 훅을 읽는 하네스에만 적용 |
| git 훅 | 실제 git 동작 — 사람·AI 공통 | `--no-verify` (그래서 deny 에도 넣는다) |
| CI | 머지 전 검증 실행 | 성공 필수·승인 필수는 **서버 설정**이며 리포가 강제하지 못한다 |

**훅은 클론 후 1회 활성화가 필요하고, 안 하면 조용히 건너뛴다.**

```bash
git config core.hooksPath script/githooks
```

## 검증 루프

모든 커밋 앞에 같은 관문이 있다.

```
코드 변경 → run-lint-test.sh ─▶ 생성물 일치(harness check)
                              ─▶ 셸 회귀 테스트
                              ─▶ 프로젝트 검증(verify-project.sh)
                                        │
                                   통과 ─▶ 커밋
                                   실패 ─▶ 커밋 안 함
```

**생성물 일치를 먼저 본다** — 설정과 어긋난 훅·권한으로 도는 상태에서 나머지를 검증해 봐야
의미가 없다. 프로젝트 검증 안에서는 계층 의존 검사를 포맷·테스트보다 먼저 둔다. 싸고, 위반이면
어차피 설계를 고쳐야 한다.
