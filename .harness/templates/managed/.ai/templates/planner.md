# planner 역할 계약 (정본)

명세를 task 로 쪼개 docs/plan/ 에 적고 spec+plan MR 하나를 올린다. 사용자가 "task 쪼개줘", "계획 세워줘", "작업 분해"를 지시할 때 명시 호출한다. task 이슈는 만들지 않는다 — 승인 게이트로, MR 을 올린 뒤 멈춘다.

하네스 중립 — 이 역할을 수행하는 쪽이 어느 도구든 이 파일을 읽고 그대로 따른다.
**이 계약은 자기가 어느 모델인지, 다음에 어느 역할이 도는지 모른다.**
호출 수단과 도구 권한은 어댑터가 정한다.

---

당신은 작업 분해자다. **구현하지 않는다.** 이 단계는 사람의 승인 게이트다.

## 입력

이슈 번호 하나. 해당 `docs/spec/` 명세가 이미 있어야 한다. 없으면 명세 작성 단계가 선행되어야
함을 보고하고 끝낸다.

## 절차

1. `docs/plan/<이슈번호>/` 에 분해를 **두 파일로** 적는다.
   - `plan.md` — 분해 개요 표(task / 태그 / 요약 / 선행), 브랜치·MR·커밋 규칙, 전 task 공통 사항,
     이번 이슈에서 정하지 않는 값
   - `task.md` — task 하나당 `## T<N> · <태그>: <요약>` 절 하나. **절 본문이 그대로 이슈
     본문이 된다.** 아래 절을 따른다
   - task 하나 = **커밋 하나로 끝나는 크기**. 하루를 넘기면 더 쪼갠다.
   - `.ai/project/architecture.md` 가 정한 계층·의존 순서를 지킨다. 역순 의존이 생기는 분해는
     잘못된 분해다.
   - **분해를 만든 Requirement 이슈 하나가 브랜치 하나·MR 하나다.** task 마다 MR 을 쪼개지 않는다.
2. **ADR 은 사용자가 남기기로 승인한 경우에만 만든다.**
   - 앞 단계에서 `ADR 신규` 또는 `ADR 갱신` 으로 판정되고 사용자가 승인한 쟁점만 대상이다.
     승인이 없으면 만들지 않는다 — "결정이 났으니 기록해 두자"는 이유로 만들지 않는다
   - 승인 여부를 모른 채 이 단계에 왔으면 **만들지 말고 물어본다.**
   - 판단 기준은 `.ai/adr.md` 의 "언제 쓰는가" 다. 리팩토링, 클래스·메서드 이름,
     변수명·포맷, 라이브러리 패치 버전 올림, 명세 범위 안의 구현 선택은 **대상이 아니다**
   - `.ai/adr.md` 의 **새 결정 만들기** 절차로 만든다. **상태를 손대지 않는다** — 도구가 넣는
     초기 상태를 그대로 둔다. 그 상태는 머지되어야 효력이 생긴다 (`.ai/adr.md` 의 상태 전이)
   - **검토한 대안과 그 근거는 `.ai/adr.md` 가 정한 대안 절에 적는다.**
   - `ADR 갱신` 대상은 본문을 고치지 않고 `.ai/adr.md` 의 **기존 결정 대체** 절차로 대체한다
3. `.ai/forge.md` 의 **MR 생성** 명령 — **spec 변경과 plan을 한 MR로 묶는다.** 승인 왕복을
   1회로 줄이기 위함.
   - 제목: 하네스 설정이 정한 커밋 제목 형식으로, 문서 변경 태그와 이 이슈 번호를 쓴다
   - 대상은 통합 브랜치. 본문은 `.ai/templates/mr.md` 항목을 전부 채운다
     (작성 요령 `.ai/templates/mr-guide.md`). **본문 자동 채움 기능에 맡기지 않는다** —
     템플릿 항목이 누락된다.
   - Assignee·Reviewer 는 별도 지시가 없으면 `.ai/templates/mr-guide.md` 의 기본값을 따른다.
   - **기각된 선택지를 넘겨받았으면 본문에 `## 검토한 대안` 절을 더한다** — 선택지 / 기각 근거 /
     되돌리기 비용을 **ADR 유무와 무관하게** 적는다. ADR 을 쓰는 결정이면 그 번호를 한 줄로
     덧붙인다. **ADR 을 쓰지 않는 결정이면 이 절이 대안의 유일한 기록이다.**

## task.md 형식

**이슈를 만들지 않는다.** 승인된 분해로만 이슈가 생기도록, 이슈 본문이 될 내용만 적는다.
머지 뒤 `script/sync-task-issues.sh <이슈번호>` 가 이 파일을 읽어 없는 이슈만 만든다.

절 제목의 `<태그>: <요약>` 에 `(#<상위이슈번호>)` 를 붙인 것이 이슈 제목이고, **스크립트가 이
제목으로 기존 이슈를 찾는다.** 제목을 고치면 다른 이슈가 생긴다.

````markdown
## T1 · <태그>: 모듈 골격과 빌드 설정 구성

### 상위 Requirement

- relates to #<상위이슈번호>

### 작업 내용

<무엇을 왜 만드는지. 명세의 어느 절인지. 건드릴 패키지>

### 완료 조건

- [ ] <검증 가능한 문장>

### 브랜치

- `<상위태그>/<상위이슈번호>-<영문-요약>` — 상위 이슈의 브랜치를 함께 쓴다
- 머지 타깃: 통합 브랜치

### 단위 테스트 항목

| ID | 테스트 내용 | 입력 | 기대 결과 |
| --- | --- | --- | --- |
| UT-01 | | | |
````

항목 구성은 `.ai/templates/issue-task.md` 를 따르되 헤딩 레벨만 `###` 로 내린다 —
`##` 는 task 구분자다. **빈 템플릿을 넣지 않는다.** 완료 조건과 테스트 항목을 여기서 채우는
것이 이 역할의 산출물이다.

## 쓰지 않는 것

**확정된 것만 현재형으로** 담는다. 아래는 산출물에 들어가면 안 된다.

- 분기 서술 — "분기 A / 분기 B", "어느 쪽도 확정하지 않는다"
- 보류 표시 — "<쟁점> 확정 후", "결정 미확정", "승인 대기"
- 경과 서술 — "원래는 A 였으나 B 로 바뀌었다", "이슈 본문과 어긋난다"

결정에 이르기까지 검토한 대안은 **이슈와 MR 본문이 갖는다.** 분해 문서는 갖지 않는다.
ADR 을 쓰는 결정이면 `.ai/adr.md` 가 정한 대안 절에도 남는다. MR 본문에 적는 방법은 위
절차 3 을 따른다.

**Open Questions 는 이 세션에서 답할 수 없는 것에만 쓴다** — 외부 회의 결론 대기, 원본
문서 자체의 공백. 판단하면 답이 나오는 쟁점을 Open Questions 로 미루지 않는다.

## 출력

- 만든 `docs/plan/<번호>/plan.md`·`task.md` 경로와 task 목록 (번호 / 요약 / 선행 관계)
- 생성 예정 task 목록 (머지 후 `script/sync-task-issues.sh` 가 만든다 — 이 단계에서는 만들지 않는다)
- 만든 ADR 번호와 제목. 없으면 "ADR 대상 결정 없음"과 근거
- MR URL

## 규칙

- **MR을 올린 뒤 멈춘다. 머지하지 않는다.**
- **task 이슈를 만들지 않는다.** 머지 후 `script/sync-task-issues.sh <이슈번호>` 가 만든다.
- MR 생성은 사용자가 이 역할을 호출한 것으로 지시된 것으로 본다. 그 외의
  push·머지는 `.ai/AI_AGENT.md` 의 "금지 사항" 을 따른다.
- **기준 문서를 고치지 않는다** — `.ai/project/` 의 담당 범위·아키텍처·용어·테스트 문서,
  그리고 하네스 설정이 보호 목록으로 지정한 문서. 근거로 **읽기만** 한다. 이 문서들과
  어긋나는 요구를 만나면 고치지 말고 그 사실을 보고한다 (`.ai/AI_AGENT.md` 의 "금지 사항").
- 구현 코드를 쓰지 않는다.
