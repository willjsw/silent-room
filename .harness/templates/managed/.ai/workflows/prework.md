# prework — 이슈 하나를 개발 착수 가능한 상태로 만든다

요구사항 검토 → 결정 게이트 → 명세 → task 분해 → ADR 초안 → spec+plan MR까지.
**결정 게이트와 승인 게이트, 두 번 멈춘다.**
하네스 중립 절차 정본. 어떻게 호출하는지는 각 하네스 어댑터가 정한다.

## 입력

이슈 번호 하나. 없으면 진행하지 않고 번호를 요구한다.

## 중단 조건 (착수 전 확인)

하나라도 걸리면 **아무것도 만들지 않고** 사유를 보고하고 끝낸다.

1. 이슈가 없거나 이미 닫혀 있다
2. 작업 트리에 **내가 만들지 않은 미커밋 변경**이 있다 (`git status --porcelain`)
   — 남의 작업을 이 MR에 끌어들이지 않는다. 사용자가 stash·커밋을 정리한 뒤 다시 부른다
3. 같은 이슈의 spec+plan MR이 이미 열려 있다

## 절차

### 1. 이슈 읽기

`.ai/forge.md` 의 이슈 조회 명령으로 본문·라벨·상위 이슈를 읽는다.
하네스 설정이 정한 태그 중 어느 것인지 파악한다.

### 2. 브랜치

`docs/<이슈번호>-<영문-요약>` 브랜치를 통합 브랜치에서 만든다. 이미 있으면 체크아웃한다.
spec+plan은 문서 변경이므로 태그는 문서 태그(`docs`)다.

### 3. 요구사항 검토 — 요구사항 검토자 역할에 위임

이슈 번호를 넘긴다. **산출물 파일은 없다** — 쟁점 보고만 돌아온다.

이 단계가 앞에 있는 이유는, 쟁점을 명세 작성 도중에 만나면 판단을 보류한 흔적
("확정 후", "분기 A / 분기 B", "결정 미확정")이 산출물에 남기 때문이다.

### 4. 결정 게이트 (사람)

검토 보고에 쟁점이 하나라도 있으면 **여기서 멈추고 사용자에게 올린다.**

- 쟁점마다 선택지·권고·근거·되돌리기 비용을 **그대로** 전달한다. 요약하면서 선택지를 지우지 않는다
- **임의로 결정하지 않는다.** 권고안이 있어도 사용자가 고르기 전에는 다음 단계로 가지 않는다
- 질문 목록의 **맨 마지막에 ADR 처리 방침을 함께 묻는다.** 검토자가 `ADR 신규` 또는
  `ADR 갱신` 으로 판정한 쟁점이 있을 때만 묻는다 — `ADR 불필요` 로 판정된 것은 묻지 않는다
  (`.ai/adr.md` "언제 쓰는가". ADR 이 많아지면 아무도 읽지 않는다)

쟁점이 없으면 이 단계를 건너뛴다. **쟁점을 만들어내서 질문을 늘리지 않는다.**

**결정된 내용은 다음 단계에 프롬프트로 넘긴다. 중간 기록 파일을 만들지 않는다.**

**기각된 선택지와 그 근거도 함께 넘긴다.** 작업 분해자가 MR 본문에 적는다 (아래 6단계).
ADR 을 쓰지 않는 결정이면 **MR 본문이 대안의 유일한 기록**이 된다 — 여기서 떨어뜨리면
"무엇을 검토하고 왜 기각했는지" 가 어디에도 남지 않는다.

### 5. 명세 — 명세 작성자 역할에 위임

이슈 번호와 **4단계에서 결정된 내용**을 넘긴다. 산출물은 `docs/spec/` 파일.

- **"명세 갱신 불필요"가 돌아오면** 그 근거(어느 문서가 이미 덮는지)를 사용자에게 보고하고
  **task 분해로 넘어갈지 확인받는다.** 임의로 진행하지 않는다.
- 인접 모듈 소관이라는 판단이 돌아오면 거기서 멈춘다.

### 6. task 분해 + ADR + MR — 작업 분해자 역할에 위임

이슈 번호와 4단계의 결정·ADR 방침을 넘긴다. 산출물은 `docs/plan/<번호>/plan.md`·`task.md`, MR,
그리고 **4단계에서 사용자가 승인한 경우에만** ADR.
**task 이슈는 여기서 만들지 않는다** — `task.md` 에 이슈 본문만 적고, 머지 후
`script/sync-task-issues.sh` 가 만든다.

### 7. 커밋·MR

- 커밋 메시지는 `docs: <요약>(#<이슈번호>)`. 명세와 PLAN을 한 커밋으로 묶어도 된다.
- MR은 spec 변경과 plan을 **하나로** 묶는다. 승인 왕복을 1회로 줄이기 위함.
- MR 본문은 `.ai/templates/mr.md` 항목을 전부 채운다. forge 도구의 자동 채움 옵션을 쓰지 않는다.
- **4단계에서 기각된 선택지가 있으면 MR 본문에 `## 검토한 대안` 절을 더한다.**
  선택지 / 기각 근거 / 되돌리기 비용을 **ADR 유무와 무관하게** 적는다. ADR 을 쓰는 결정이면
  그 번호를 한 줄로 덧붙인다 — MR 만 보는 사람도 기각 근거를 읽을 수 있어야 한다.

### 8. 결정 역추적

4단계 결정 중 **이슈 본문의 요구와 어긋나는 것**이 있으면 해당 이슈에 댓글 1건을 남긴다.
어긋난 결정이 없으면 이 단계를 건너뛴다.

어긋났는지는 새로 판정하지 않는다. **요구사항 검토가 쟁점의 출처를 `이슈 본문 ↔ docs/` 로
적은 것 중, 이슈 본문과 다르게 결정된 것**이 대상이다.

- 댓글에 담는 것: 어긋난 요구 문장(원문 인용) · 결정 · 근거 문서 · ADR 번호 · MR URL
- **이슈 본문은 고치지 않는다.** 요구 기록은 사람의 것이고, 본문을 결정 결과로 덮으면
  "무엇을 요구했는가" 와 "무엇으로 결정됐는가" 가 한 문장에 섞여 ADR 의 전제(대안이 실제로
  제기됐다는 사실)가 사라진다. 본문 갱신이 필요하면 사람이 한다
- 댓글은 결정을 **다시 여는 것이 아니라 가리키는 것**이다. 검토한 대안과 기각 근거는 MR
  본문에 있고 댓글에 옮겨 적지 않는다 ("산출물에 남기지 않는 것")
- 본문이 명시하지 않아 **해석을 확정한 것**은 어긋남이 아니다. 필요하면 참고로 한 줄만 적는다

## 출력

```
## prework 결과 (#<이슈번호>)

- 브랜치: docs/<번호>-<요약>
- 검토한 쟁점: <N>건 (결정 완료)   (또는 "쟁점 없음")
- 명세: docs/spec/<파일>          (또는 "갱신 불필요 — <근거>")
- 계획: docs/plan/<번호>/plan.md · task.md  (task N건)
- 생성 예정 task: <N>건 (머지 후 script/sync-task-issues.sh <번호> 로 생성)
- ADR: <번호> <제목>   (또는 "ADR 대상 결정 없음 — <근거>",
                                    또는 "ADR 대상이나 사용자가 남기지 않기로 함")
- MR: <URL>
- 이슈 역추적: #<이슈번호> 댓글 (본문과 어긋난 결정 <N>건)   (또는 "해당 없음")

### 확인이 필요한 것
- <!-- TBD --> 로 남긴 항목
- Open Questions 에 추가한 쟁점
```

## 산출물에 남기지 않는 것

**결정을 고민한 흔적을 문서에 남기지 않는다.** 4단계에서 결정이 났으므로, 명세와 PLAN 은
확정된 것만 현재형으로 쓴다. 아래는 산출물에 들어가면 안 된다.

- 분기 서술 — "분기 A / 분기 B", "어느 쪽도 확정하지 않는다"
- 보류 표시 — "<쟁점> 확정 후", "결정 미확정", "승인 대기"
- 경과 서술 — "원래는 A 였으나 B 로 바뀌었다", "이슈 본문과 어긋난다"
- 결정되지 않은 쟁점을 담는 Open Questions 행 — 4단계를 거쳤으면 이미 결정됐다

**검토한 대안은 이슈와 MR 본문에 적는다.** 명세·분해 같은 현재형 산출물은 "지금 무엇이
사실인가"만 담는다 (`.ai/AI_AGENT.md` "문서 지도"). ADR 을 쓰는 결정이면 그 `## Context` 에도 남는다 —
ADR 은 결정의 로그이므로 거기에 대안과 근거가 있는 것이 정상이다.

Open Questions 는 **4단계로 해결되지 않는 것**에만 쓴다 — 외부 회의 결론 대기, 원본
문서 자체의 공백처럼 이 세션에서 답할 수 없는 것. 답할 수 있는 쟁점을 Open Questions 로
미루지 않는다.

## 멈추는 지점

**MR을 올리고 결정 역추적까지 마친 뒤 멈춘다.** 머지하지 않고, 구현을 시작하지 않는다.
사용자가 MR을 머지한 뒤 구현 절차(`work`)로 진행한다 — task 이슈 생성은 그 첫 단계에서
`script/sync-task-issues.sh` 가 한다.

**ADR 상태를 손대지 않는다.** 초안이 갖는 상태는 `.ai/adr.md` 가 정하고, **결정의 효력은
통합 브랜치 머지에서 생긴다** (`.ai/adr.md` 상태 전이). 따로 올리는 단계가 없다.
