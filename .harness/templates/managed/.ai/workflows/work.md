# work — 이슈 하나를 구현하고 리뷰 루프를 돈다

task 이슈 동기화 → 구현 → MR → 리뷰 → 수정 → 재리뷰.
**판정이 PASS 가 되거나, 상한에 닿거나, 고칠 것이 남지 않으면 멈춘다.**
하네스 중립 절차 정본. 어떻게 호출하는지는 각 하네스 어댑터가 정한다.

## 입력

**이슈 번호 하나.** 없으면 진행하지 않고 번호를 요구한다.

경로는 **분해(`docs/plan/<번호>/`)의 유무**가 가른다. 이슈 라벨이나 제목으로 판정하지 않는다.

**판정은 `script/work-preflight.sh` 하나가 한다.**

```bash
script/work-preflight.sh <이슈번호>
# stdout: plan | standalone   ·   종료 코드: 0 착수 가능 · 1 착수 불가 · 2 실행 실패
```

**판정을 절차에 풀어 적지 않는다.** 두 곳에 적으면 한쪽에 검사를 더할 때 다른 쪽이 낡는다.
스크립트가 세 가지를 이 순서로 본다.

| 순서 | 검사 | 실패하면 |
|---|---|---|
| ① | 이슈에 열린 MR 이 있는가 | 착수 불가 — 승인 대기 중인 spec+plan MR 이거나 이미 도는 구현이다 |
| ② | 원격의 통합 브랜치에 `docs/plan/<번호>/task.md` 가 있는가 | 없으면 `standalone` |
| ③ | 같은 ref 에 `docs/spec/<번호>-*.md` 명세가 있는가 | 분해만 있고 명세가 없으면 착수 불가 |

**①이 ②보다 먼저인 것이 중요하다.** 두 검사 사이에 spec+plan MR 이 머지될 수 있는데,
분해를 먼저 보면 "분해 없음(t0) + 열린 MR 없음(t1)" 이 되어 단독 task 로 오판한다.
순서를 지키면 같은 경합이 "분해 있음" 쪽으로 떨어진다.

판정은 로컬 작업 트리를 보지 않는다. 로컬이 낡으면 이미 머지된 분해를 놓친다.

## 중단 조건 (착수 전 확인)

하나라도 걸리면 **아무것도 만들지 않고** 사유를 보고하고 끝낸다.

1. 이슈가 없거나 이미 닫혀 있다
2. 작업 트리에 **내가 만들지 않은 미커밋 변경**이 있다 (`git status --porcelain`)
3. **`script/work-preflight.sh <번호>` 가 0 이 아니다.** 사유는 스크립트가 stderr 로 낸다.
   - 열린 MR 이 있다 — 승인 대기 중인 spec+plan MR 이거나 이미 도는 구현이다
   - 분해는 있는데 명세가 없다 — 완료 조건의 근거가 가리키는 곳이 없다
   - 종료 코드 2 는 조회·fetch 실패다. **"없음" 이 아니다.** 멈추고 출력을 그대로 보고한다
4. 판정이 `standalone` 인데 **이슈 본문에 완료 조건이 없다.** 무엇을 하면 끝인지가 적혀 있어야
   한다. 제목과 한 줄 요약만 있는 이슈는 근거가 아니다 — `prework` 를 먼저 돌린다.

판정이 `plan` 이면 분해와 명세가 원격의 통합 브랜치에 있다는 뜻이고, 그것이 곧 승인을
거쳤다는 뜻이다. `standalone` 이면 그 이슈 본문이 승인된 작업 지시다.

## 루프

```
  (분해 있음) task 이슈 동기화 ─┐
                                ├─▶ 구현자 ──MR 번호──▶ 리뷰 ──종료 코드──┐
  (분해 없음) ──────────────────┘      ▲                                 │
                                       └─────── 1 = 재시도 (리뷰 본문) ───┘
```

**구현과 리뷰는 서로 다른 도구가 맡는다.** 같은 모델이 자기 코드를 리뷰하면 같은 맹점을
두 번 지나간다. 어느 도구인지는 이 절차가 알지 않는다 — 스크립트와 어댑터가 정한다.

### 1. task 이슈 동기화 — `script/sync-task-issues.sh <Requirement 이슈번호>`

**판정이 `plan` 일 때만 돈다.** `standalone` 이면 이 단계를 건너뛰고 2단계로 간다 —
그 이슈 자신이 구현 단위이므로 만들 하위 이슈가 없다. 스크립트를 부르지 않는다.

```bash
script/sync-task-issues.sh <이슈번호>
```

`docs/plan/<번호>/task.md` 의 각 절을 이슈 제목으로 대조해 **없는 것만 만든다.** 이미 열려 있거나
닫힌 이슈는 건너뛴다. 출력은 `T1 #6 skip(opened)` 형식의 매핑이고, 구현자가 커밋 메시지의
이슈 번호를 여기서 얻는다.

- 종료 코드가 0이 아니면 **구현을 시작하지 않는다.** 이슈 번호 없이는 커밋이 훅에 막힌다.
- 스크립트는 로컬 작업 트리가 아니라 **방금 fetch 한 원격 통합 브랜치의 `task.md` 를 읽는다.** 승인된
  분해로만 이슈가 생긴다는 게이트를 스크립트 자신이 지킨다
  머지 전이면 여기서 멈추므로 착수 판정의 열린 MR 검사와 층이 겹친다.

### 2. 구현 — 구현자 역할에 위임

**착수 직전에 `script/work-preflight.sh` 를 한 번 더 돌린다.** 결과가 처음과 다르면
위임하지 않는다 — 그 사이 원격이 바뀐 것이다. `plan` 으로 바뀌었으면 1단계부터 다시 가고,
착수 불가로 바뀌었으면 멈춘다.

이슈 번호를 넘긴다. 분해가 있으면 **1단계의 task↔이슈 매핑**을 함께 넘기고, 없으면 넘기지
않는다 — 구현자가 이슈 본문을 완료 조건으로 읽는다. 산출물은 어느 경로든 브랜치 1개·MR 1개.

- 검증(`script/run-lint-test.sh`)이 실패하면 구현자는 커밋하지 않는다.
  그 상태로 돌아오면 **루프를 돌리지 말고 멈춘다.** 실패 출력을 그대로 보고한다.
- MR 번호를 받지 못하면 루프를 시작할 수 없다. 멈추고 사유를 보고한다.

### 3. 리뷰 — `script/review-mr.sh <MR번호>`

```bash
script/review-mr.sh <MR번호>
```

스크립트가 diff를 받아 리뷰 도구에 넘기고, 결과를 MR 댓글로 등록한 뒤 판정을 종료 코드로
돌려준다. **어느 도구가 리뷰하는지는 스크립트 상단이 정한다.**
**리뷰 대상은 그 MR 의 변경 전체**다 — 분해가 있으면 전 task 의 변경 합, 없으면 단독 task 의 변경이다.

**회차와 상한도 이 스크립트가 관리한다.** 실행할 때마다 회차 라벨을 스스로 올리고, 상한에
닿으면 리뷰를 수행하지 않는다. **절차도 세션도 라벨을 손대지 않고 회차를 세지 않는다** —
세는 쪽과 멈추는 쪽이 같으면 세지 않은 회차가 그대로 상한 밖이 된다.

| 종료 코드 | 뜻 |
|---|---|
| 0 | blocker·major 0건 — minor 만 남아도 여기다 |
| 1 | blocker·major 1건 이상 |
| 2 | 리뷰를 수행하지 못함 (도구 없음·diff 조회 실패·출력 계약 위반 = `REVIEW_VERDICT` 선언 누락 또는 `## 발견 사항` 절 누락·제목 수준 위반·회차 갱신 실패·등록 실패) |
| 3 | **상한** — 회차 상한에 닿았거나 같은 blocker·major 지적이 반복됐다 |

- 역할 계약(점검 항목·반증 절차·출력 계약)은 스크립트가 아니라 `.ai/templates/code-reviewer.md`가 갖는다.
- **판정은 발견 등급 집계로 한다.** 루프를 끝낼지는 blocker·major 건수가 정하고, minor 는 세지
  않는다. 본문 마지막 줄의 `REVIEW_VERDICT` 는 **계약 준수 여부를 보는 용도**다 — 선언이 없으면
  등록하지 않고 종료 코드 2, 선언과 집계가 다르면 집계를 따르되 그 사실을 요약에 남긴다.
  기준의 정본은 `.ai/templates/code-reviewer.md` "판정의 정본은 등급 집계다" 절이다.
- **집계는 `## 발견 사항` 절 안만 센다.** 판정이 집계인 이상 절 밖의 등급 형식 줄이 판정을 바꾸면
  안 된다. 절 제목은 수준까지 정확히 `## 발견 사항` 이고, 절은 다음 제목에서 끝난다.
  절이 없거나 제목 수준이 다르거나 절 안이 비어 있으면 선언 누락과 같이 종료 코드 2 이고,
  루프를 진행하지 않는다.
- **종료 코드 2는 "PASS"가 아니다.** 루프를 진행하지 말고 멈춘 뒤 스크립트 출력을 그대로 보고한다.
  등록에 실패해도 리뷰 본문은 표준 오류로 나오므로 유실되지 않는다.
- **리뷰 수단은 이 스크립트 하나다.** 회차를 올리고 상한에서 멈추는 곳이 여기뿐이라, 이를
  거치지 않는 리뷰 경로는 상한 없는 루프가 된다. 절차는 두 번째 경로를 두지 않는다.
  다른 도구로 리뷰해야 하면 스크립트 상단의 리뷰어 지정을 바꾼다 — 리뷰어만 바뀌고 회차·상한·
  등록은 같은 경로를 탄다. 발견을 diff 라인에 다는 **인라인 등록도 이 경로가 이미 한다.**

### 4. 분기 — 종료 코드로만 한다

| 종료 코드 | 다음 |
|---|---|
| 0 | **4-1 마무리를 먼저 돈다.** 그 뒤 루프 종료, 성공 보고. **머지하지 않는다.** 남은 minor 를 함께 보고한다 |
| 1 | 구현자를 **재시도 모드**로 다시 부른다 — 리뷰 본문을 그대로 넘긴다. **돌아왔을 때 코드가 바뀌지 않았으면 재리뷰하지 않는다**(5-1) |
| 2 | 멈춘다. 스크립트 출력을 그대로 보고한다 |
| 3 | 멈춘다. **MR을 닫지 않고** 열어 둔 채 사람에게 넘긴다 |

#### 4-1. 마무리 — PASS 로 끝내기 전 한 번

**남은 발견의 처리를 MR 에 남기고 끝낸다.** 종료 코드 0 은 blocker·major 가 0 건이라는 뜻이지
발견이 없다는 뜻이 아니다. 루프가 끝나면 무엇을 왜 고치지 않았는지 남길 자리가 사라진다.

**언제 도는가.** 종료 코드 0 이고, 그 회차 리뷰 본문의 `## 발견 사항` 절에 **아직 처리가 MR 에
남지 않은 발견**이 있을 때. 남는 것은 minor 뿐이다 — 범위 밖 표기는 등급을 낮추지 않으므로 범위 밖
blocker·major 는 종료 코드 1 로 재시도 경로를 타고, 거기서 코드가 바뀌지 않으면 5-1 이 받는다.
발견이 없거나 전부 이전 회차에 처리됐으면 이 단계를 건너뛴다.

**무엇을 넘기는가.** 구현자를 **마무리 모드**로 **한 번** 부른다. 이슈 번호·MR 번호·리뷰 본문
전체를 넘기고 아래를 명시한다.

- **코드를 고치지 않는다.** 남은 발견마다 처리를 MR 에 남기는 것이 이번 호출의 전부다
- **남는 것이 minor 뿐이라 답글을 달 스레드가 없다.** minor 는 인라인에서 빠지므로 그 처리는
  **새 MR 노트**에 어느 발견인지 지목해 적는다. 자리를 가르는 것은 등급이 아니라 **스레드 유무**이고,
  그 기준의 정본은 `.ai/templates/developer.md` 다
- 무엇을 어디에 적는지는 `.ai/templates/developer.md` "고치지 않고 넘기는 지적" 절이 정한다 —
  범위 밖이면 이월 이슈 번호 또는 만들지 않은 사유, 오탐이면 반증 근거
- 고쳐야 한다고 판단되면 고치지 말고 사유와 함께 보고한다. 코드가 바뀌면 재리뷰가 필요한데
  이 단계는 재리뷰를 돌지 않는다

**그 뒤.** 재리뷰하지 않는다 — 코드가 그대로라 같은 diff 를 다시 보는 것이고 회차만 쓴다.
구현자가 돌아오면 남은 발견마다 그 처리가 MR 에 있는지 확인하고 출력의 "남은 것" 에 적은 뒤
루프를 끝낸다. **비어 있어도 구현자를 다시 부르지 않는다** — 그 사실을 보고에 남기고 사람에게 넘긴다.

종료 코드 1·2·3 에는 이 단계를 두지 않는다. 1 은 다음 회차가, 2·3 은 MR 을 열어 둔 채 받는
사람이 그 자리를 갖는다.

### 5. 상한

**회차와 반복 지적은 스크립트가 세고 스크립트가 멈춘다.** 절차는 그 종료 코드를 따르기만 한다.

| 상한 | 무엇이 강제하나 |
|---|---|
| **주** — 리뷰 회차 (회차 라벨) | `script/review-mr.sh` — 상한에서 리뷰를 수행하지 않고 종료 코드 3. `--force` 를 명시할 때만 넘어간다 |
| **보조** — 한 파일에 blocker·major 가 연속으로 나오는 회차 | `script/post-review.sh` — 회차별 발견을 파일 경로로 누적하고 연속 회차가 상한에 닿으면 종료 코드 3 |

**둘의 신뢰 수준이 다르다.** 회차 라벨은 원격 MR 에 붙으므로 어느 기기에서 이어 돌리든 유지되고,
루프가 끝난다는 보장은 여기서 나온다. 반복 카운트는 실행 환경의 로컬 파일에 쌓여 **다른 기기·새
클론에서는 0 부터 다시 센다** — "한 파일이 회차마다 다시 걸리면 명세가 틀린 것" 을 회차 상한보다 먼저 잡는
신호이지 루프의 종료 보장이 아니다. 초기화돼도 회차 상한이 남는다.

상한에 닿으면 코드를 더 고치지 않는다. 반복 지적으로 멈췄으면 **코드가 아니라 명세가 틀린
것이므로**, 근거와 함께 명세 단계로 되돌릴 것을 제안한다.

아래 셋은 스크립트가 보지 못하므로 절차가 판단한다.

- 구현자가 검증 실패로 커밋하지 못했다. **5-1 보다 먼저 본다** — 이때도 `HEAD` 는 그대로다.
- 리뷰어가 `blocker`로 "설계와 상충하는 인터페이스 변경"을 지적했다 —
  이건 코드 수정으로 덮을 문제가 아니다. 사람 판단을 받는다.
- **재시도 회차에서 코드가 하나도 바뀌지 않았다** — 5-1.

어느 쪽이든 **MR을 닫지 않는다.** 열어 둔 채 사람에게 넘긴다.

#### 5-1. 코드가 바뀌지 않은 재시도 — 재리뷰하지 않고 넘긴다

구현자가 blocker·major 를 **전부 이월하거나 반증해 커밋을 남기지 않은** 회차다. 검증 실패로
커밋하지 못한 것은 위 첫 항목이 받는다. **두 경우 모두 `HEAD` 가 그대로여서 `HEAD` 만으로는
가르지 못한다** — 구현자 보고와 작업 트리가 가른다.

**왜 멈추는가.** 리뷰어는 diff 와 리포 원본만 보는 것이 아니라 **직전 회차의 지적과 그에 달린
답글까지 입력으로 받는다**(`script/README.md` "리뷰 입력은 diff 만이 아니다"). 그래도 코드가
그대로면 재리뷰가 판정을 바꾸지 못한다.

- **이번 회차에 볼 변경이 없다.** 2회차 이후 리뷰어가 먼저 보는 것은 증분 diff 인데, 커밋이
  없으면 기준 리비전이 현재 리비전과 같아 그 절이 "직전 리뷰 이후 커밋이 없다" 로 나간다.
  누적 diff 는 직전 회차와 같은 것이다.
- **이월한 blocker·major 는 그대로 다시 집계된다.** 범위 밖 표기는 등급을 낮추지 않고 판정은
  등급 집계라, 코드를 고치지 않는 한 종료 코드는 1 그대로다. 회차를 거듭해 봐야 반복 지적
  상한에서 3 으로 멈추고 결론은 같은 자리로 온다.
- **반증을 받아들일지는 리뷰어의 재판단이고 구현자가 더 할 수 있는 일이 아니다.** 근거는 이미
  답글에 있고, 그것을 검토하는 것은 다음 회차가 아니라 MR 을 받는 사람의 몫이다.

루프는 코드를 고쳐 판정을 바꾸는 장치이므로 고칠 것이 없으면 돌지 않는다.

**어떻게 아는가. 두 단계이고 순서가 있다.**

1. **검증 실패를 먼저 배제한다.** 구현자가 `script/run-lint-test.sh` 실패로 커밋하지 못했다고
   보고했거나, 작업 트리에 커밋되지 않은 변경이 남아 있으면(`git status --porcelain`) 이 절이
   아니라 상한 절 첫 항목이다. 고칠 것이 없었던 게 아니라 검증에서 막힌 것이므로, 실패 출력을 그대로
   보고하고 멈춘다.
2. 그 뒤 구현자를 부르기 전과 돌아온 뒤의 `git rev-parse HEAD` 를 비교한다. 같으면 커밋이 없는
   것이다 — **구현자가 고쳤다고 말해도 커밋이 없으면 코드는 그대로다.**

**순서를 뒤집지 않는다.** `HEAD` 부터 보면 검증 실패가 이월·반증으로 오분류되어 실패 출력이
"고칠 것이 없었다" 로 묻힌다.

**무엇을 하고 끝내는가.** 남은 blocker·major 마다 그 처리가 MR 에 있는지 확인한다. 이월이면 이슈
번호, 오탐이면 반증 근거다. **어디를 보는지는 등급이 아니라 스레드 유무가 정한다** — 인라인
스레드가 달린 발견은 그 답글에, 스레드가 없는 발견(`파일:라인` 형식을 어겼거나 이번 diff 에 없는
줄을 가리켜 인라인이 빠진 것)은 새 MR 노트에 있다. 없으면 그 사실을 출력의 "남은 것" 에 적는다. **비어 있어도 구현자를
다시 부르지 않는다.** 그 뒤 재리뷰하지 않고 MR 을 열어 둔 채 사람에게 넘긴다. 최종 판정은
`중단` 이고, 사유에 무엇이 남아 멈췄는지를 적는다.

**범위 밖인지는 리뷰어가 먼저 판정하고 구현자도 판정할 수 있다.** 어느 쪽이든 판단과 근거는
MR 에 남는다 — 리뷰어 표기는 등록된 리뷰 본문에, 구현자 판단은 답글에 있다
(`.ai/templates/developer.md` "고치지 않고 넘기는 지적"). **절차가 멈추는 근거는 그 판정이 아니라
코드가 바뀌지 않았다는 관측이다.** 판정이 옳든 그르든 MR 은 열린 채 사람에게 가고, 판정을
검토할 자리는 거기다.

## 출력

```
## work 결과 (#<이슈번호>)

- 브랜치: <태그>/<번호>-<요약>
- task 이슈: T1 #6 · T2 #7 · … (생성 <N>건 / 기존 <N>건)   (또는 "해당 없음 — 분해 없는 단독 task")
- MR: <URL>  (리뷰 루프 N회)
- 최종 판정: PASS(blocker·major 0건) | 상한 도달(회차 | 반복 지적) | 중단(<사유>)
- 검증: script/run-lint-test.sh <통과|실패>

### 루프 기록
| 회차 | 리뷰 발견 (blocker/major/minor) | 조치 |
|---|---|---|
| 1 | 2 / 1 / 3 | … |
| 2 | 0 / 0 / 1 | … |

### 남은 것
- 미해결 발견과 그 사유 — 고치지 않고 넘긴 것은 이월 이슈 번호 또는 반증 근거를 함께
- 반복된 지적이 있으면 그 내용과 명세 되돌림 제안
```

## 하지 않는 것

- MR 머지, 이슈 종료 — 사람이 한다. **task 이슈도 닫지 않는다.**
- 리뷰 스레드 resolve — 조치했다는 답글만 남기고 닫는 것은 리뷰어·사람이 한다.
- `docs/plan/<번호>/task.md` 수정 — 승인된 분해다. 어긋나면 고치지 말고 보고한다.
- 이슈 본문 수정 — 단독 task 경로에서 이것이 완료 조건의 정본이다. 어긋나면 보고한다.
- 명세에 없는 기능 추가 — 필요해 보이면 보고한다.
- 판정을 통과시키기 위한 테스트 약화·assertion 삭제.
